# Commit conventions

Use Conventional Commits with a focused scope, for example `docs: establish architecture foundation`. Keep documentation and implementation changes separable when practical. Commit messages should describe the user-visible contract or engineering outcome, not an internal chat/task number.

For non-trivial changes, include a body explaining the contract or invariant changed, validation performed, and known limitations. Reference an ADR or issue when one exists. Do not combine unrelated formatting, dependency upgrades, or generated files with a contract change.
